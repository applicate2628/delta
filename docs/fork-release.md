# Personal release packaging

## Identity and decision

The personal fork uses application ID `io.github.applicate2628.delta`, label
`Delta`, version code `100`, and version name `2026.11.03.1`. Keep this ID and
one private signing key for future updates; increment the version code for
each delivered update. The upstream and debug application IDs are unchanged.

The normal `release` build enables R8 optimization and resource shrinking.
LeakCanary and preview tooling remain debug-only dependencies. Release is
not debuggable. No new Android permissions or application behavior are added.

Alternatives rejected: replacing the upstream package would conflict with
its author's signing key; shipping another ephemeral debug-key build would
repeat the uninstall/data-migration problem. The chosen fork flavor separates
application identity from build type without changing existing flavors.

## Build and verify

```sh
./gradlew test spotlessCheck :app:assembleForkRelease
```

The manual `SoftAP regression` workflow accepts `release=true`. It checks the
package ID, label, version, absence of the debuggable flag, absence of LeakCanary
launcher entries and runtime dependencies, APK alignment, and unsigned state.
Its artifact is explicitly named `release-unsigned`: it is NOT installable
until signed. Successful compilation does not prove device behavior.

## Permanent signing

Generate a private PKCS12 keystore using the JDK `keytool`, keep it outside
Git and trash, and retain a protected offline backup. Do not publish the
keystore or password in this repository, workflow artifacts, or logs. Record
the public signing certificate SHA-256 with every delivery. An existing key
must never be overwritten or regenerated by a normal build.

Sign the verified unsigned APK with Android SDK `apksigner`, taking the
password interactively or from a protected environment/file rather than a
literal command argument. Then run `apksigner verify --verbose --print-certs`
and verify the APK identity again before installation. This branch does not
create signing keys, upload signing credentials, or silently use debug keys.

## Device migration and acceptance

Install beside `dev.shadoe.delta.debug`; do not uninstall the working build
first. Export existing presets using Delta's Export/Import feature and keep
a private backup. Import through the normal release UI; `run-as` is not
available for a non-debuggable release. Do not put private databases into an
APK or public artifact. Regrant Shizuku access to the new application when
needed. Verify saved presets, normal startup, limited mode, Wi-Fi 6 controls,
and unchanged active hotspot configuration before retiring the debug build.

Packaging verification, signing, installation, migration, and actual radio
behavior are separate acceptance checks; report their outcomes separately.
